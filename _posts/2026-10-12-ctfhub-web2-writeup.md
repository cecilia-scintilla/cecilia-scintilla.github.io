CTFHub - 302跳转 Writeup（用 Burp 看原始响应）

一、题目信息

- 平台：CTFHub（技能树 → Web → HTTP 协议 → **302 跳转**）
- 题型：Web
- 考点：HTTP 重定向（302）、**响应头 Location**、禁止客户端自动跟随跳转

二、题目分析

**① 先搞懂 302 是什么**

```text
301 / 302 都是"重定向"状态码，意思是：
    服务器说"你要的资源不在这儿，去另一个地址拿"

区别：
    301 = 永久重定向（资源搬家了，以后都去新地址）
    302 = 临时重定向（这次先去新地址，旧地址还有效）

关键：浏览器拿到 301/302 后，会"自动"跳转到响应头 Location 里写的那个新地址。
     这个过程叫"跟随重定向（follow redirect）"，用户完全无感 ——
     你只会看到地址栏一变、页面一换，根本不知道中间发生过跳转。
```

**② 这题的问题出在哪**

- 打开题目页面，上面有个类似 **"Give me Flag"** 的按钮/链接；
- 点它 —— **页面闪一下就变了，什么也没发生，flag 看不到**；
- 原因就是：**这个链接返回的是 302，浏览器自动跟随跳转到了另一个页面**，你看到的是跳转之后的页面，而**关键信息（flag）藏在那次"跳转本身"的响应里**。

**③ 破题思路**

```text
要看到 flag，就必须阻止"自动跟随跳转"，直接查看那个原始的 302 响应。

方法就是：用能"不跟随重定向"的工具发请求 ——
    · Burp Suite 的 Repeater（推荐，社区版就有）
    · curl 不加 -L 参数
    · Python 里禁用重定向处理

这样你就能看到完整的 302 响应头和响应体，flag 就在里面。
```

三、解题步骤

**方法一：Burp Suite**

```text
① Burp → Proxy → Intercept on（或直接开 Open browser 操作）
② 用 Burp 浏览器打开题目地址
③ 点击页面上那个 "Give me Flag" 按钮
④ 请求被拦下 → 点 Forward 放行

⑤ 关键一步：去 Proxy → HTTP history（历史记录）
   → 找到那条返回 302 的请求
     （列表里 Request 列会显示 302，或在 Response 列看到）
   → 右键它 → Send to Repeater（或按 Ctrl+R）

⑥ 切到顶部 Repeater 标签
   → 点【Send】
   → 看右侧 Response 区域：
        ┌──────────────────────────────────────┐
        │ HTTP/1.1 302 Found                   │  ← 状态码 302
        │ Location: /index.php                 │  ← ★ 跳转目标在这里
        │ Set-Cookie: ...                      │
        │ Content-Type: text/html              │
        │                                      │
        │ ctfhub{xxxxxxxxxxxxxxxx}             │  ← ★ 或者 flag 直接在响应体里
        └──────────────────────────────────────┘
⑦ 复制 flag 提交
```

> **为什么 Repeater 里能看到？** 因为 Repeater **不会自动跟随重定向** —— 它把服务器返回的原始响应原样给你看，包括 302 状态码和所有响应头。

**方法二：curl（命令行，一条命令）**

```powershell
# 不加 -L：不跟随跳转，能看到原始 302 响应
curl.exe -i "http://challenge-xxx.sandbox.ctfhub.com:10800/index.php"

# 对比：加了 -L 就会自动跟随跳转，看到的变成跳转后的内容
curl.exe -i -L "http://challenge-xxx.sandbox.ctfhub.com:10800/index.php"
```

- `-i` = 输出里带上**响应头**（不加的话只看得到响应体）
- **不加 `-L`** = 不跟随重定向 ← 这一步是关键

你会看到类似这样的输出：

```http
HTTP/1.1 302 Found
Location: /index.php
Content-Type: text/html

ctfhub{xxxxxxxxxxxxxxxx}
```

```text
[① 自动跟随跳转]（默认行为，相当于浏览器）
   最终状态码: 200            ← 已经不是 302 了，跳转被跟随掉了
   Location 头: (看不到，因为已经跳过去了)

[② 禁止跟随跳转]（Burp Repeater / curl 不加 -L 就是这样）
   状态码: 302                ← 拿到原始的 302
   Location 头: /get          ← ★ 跳转目标暴露出来了
```

这就是为什么必须在 Burp / curl 里看，而不是在浏览器里看 —— **浏览器只会给你看"跳转之后"的结果**。

四、延伸知识：重定向相关

**① 各种重定向状态码**

| 状态码 | 含义 | 特点 |
|---|---|---|
| `301` | 永久重定向 | 搜索引擎会更新索引，浏览器会缓存 |
| `302` | **临时重定向**（本题） | 每次访问都会重新跳转，不缓存 |
| `303` | See Other | 强制用 GET 方法访问新地址（常出现在 POST 之后） |
| `307` | 临时重定向（保方法） | 和 302 类似，但**严格保持原请求方法**（POST 还是 POST） |
| `308` | 永久重定向（保方法） | 301 的"保方法"版本 |

**② 为什么 302 会是安全考点**

```text
· 认证绕过：某些系统先跳转到登录页，如果在跳转前就吐了敏感信息，就能被截获
· 开放重定向（Open Redirect）：如果 Location 的值来自用户输入且未校验，
  攻击者能构造 ?url=http://evil.com 把用户骗到钓鱼站
· SSRF 配合：服务器端跟随跳转时，可能被引导去访问内网地址
· CTF 里最常见的就是本题这种："关键信息藏在跳转响应里，你得学会不跟随"
```

**③ 浏览器里怎么看重定向（顺带一提）**

Chrome 的 F12 → Network 面板里，重定向的请求会显示 `302`，点它能看到 `Response Headers` 里的 `Location`。**但**：

- 前提是你要**先打开 F12** 再操作（否则记录已经过去了）
- 而且很多情况下响应体在跳转后就刷掉了，不如 Burp 的 Repeater 干净

所以做 CTF 还是**用 Burp** 最稳。

五、总结

- **本题核心：浏览器会自动跟随 301/302 跳转，你必须用"不跟随"的工具才能看到原始响应。**
  记住这个组合：**Burp Repeater** 或 **curl 不加 `-L`**。
- 一条经验：**提交请求后如果"什么都没发生"或者"页面莫名其妙变了"，第一反应就去 Burp 的 HTTP history 里看那个请求的原始响应** —— 大概率有 302/301，或者响应头里有猫腻。
- CTFHub「HTTP 协议」系列到这里的进度：

```text
✅ 请求方式   —— 自定义 HTTP 方法（GET → CTFHUB）
✅ 302跳转    —— 本题：不跟随重定向，看原始响应
⬜ Cookie     —— 修改 Cookie 里的值伪造身份（admin=0 → admin=1）
⬜ 基础认证   —— Authorization 头 + Base64 + 字典爆破
⬜ 响应包源代码 —— F12 看页面源码
```

- 这几题串起来其实就是一句话：**HTTP 请求和响应的每个字段都可以做手脚，而 Burp 就是让你能改/能看这些字段的工具。**
